# BE72 离线设备历史混入 BE50：排查与修复

## 已确认的来源

问题存在于 BE72 Hub 的 SQLite 历史中。修复前，`/api/sync/snapshot` 返回的 28 台离线设备中，有 8 台的最后地址来自 BE50 的 `192.168.110.*` 网段。它们的归档和相关事件集中在 2026-09-28，事件来源标记为 `durable_device_snapshot`。

BE72 的当前在线设备来自 `192.168.5.*`。BE50 使用独立容器和数据目录，归档中没有 BE72 网段的设备。BE72 relay 的当前上报目标是自己的 Hub，已通过路由器 SSH 核对。历史来源字段无法进一步证明 9 月 28 日是哪次配置操作造成了混入，因此没有把猜测当作根因。

SQLite 的 `documents` 表是当前持久化来源，旧 JSON 文件只是迁移输入。只编辑旧 JSON 文件不会修复 APP 返回的数据。

## 修复范围

- 以路由器序列号核对修复目标，并逐条匹配已确认的 MAC、地址和日期。
- 从 BE72 活跃历史中移出 8 条错误归档、220 条相关事件、9 月 28 日的 8 条设备统计。
- 保存完整 SQLite 备份和可查看的隔离记录，不按 MAC 全局删除；同一 MAC 在正确路由器上的其他观察记录保留。
- BE50 容器和历史没有修改。仅短暂重启 BE72 Hub，未重启路由器或 relay。

NAS 备份目录：`/volume1/docker/labprobe-hub/backups/device-isolation-20261008/device-history-repair-20261008-210840-422209/`。

其中 `labprobe-before.db` 是修复前的数据库，`quarantine.json` 包含移出的记录和修复计划。原存储模块另存为上级目录的 `labprobe_storage.before.py`。

## APP 缓存重新校准

离线卡片是 APP 独立保留的缓存，删除 Hub 事件不会自动删除已经存在的离线卡片。此前设备归档不产生增量修订，归档清理后 APP 可能继续显示旧数据。

本次在归档成员被移除时记录 `system / snapshot_reset`。客户端旧游标访问增量接口时得到 `fullRequired=true`，已有 APP 会重新读取完整快照。正常的信号、流量和时间戳采样仍然不增加归档修订，避免扩大数据库。

用户无需清除 APP 数据或重新安装，回到 BE72 刷新即可重新校准。

## 校验

- 修复后 BE72 离线设备接口为 20 条，没有上述 BE50 归档。
- BE72 的错误上下线事件和当天统计已移出；BE50 归档仍为 26 条。
- 8 项历史修复和缓存校准测试通过，包括错误序列号拒绝、只预览不修改、同 MAC 不同地址/日期保留、仍在线观察拒绝删除、重复执行无修改、修订分页前检查校准边界。
- 5 项现有 SQLite 迁移、修订保留和高频采样测试通过。
- 在运行中的 BE72 Hub 上，修复前的游标得到 `fullRequired=true`，完整快照返回 20 条正确离线记录。
- 应用宝 ADB 入口可用，APP 为 0.13.83；临时调试网络未获得有效读回，因此没有把模拟器测试计入 APP 整链路验收。原连接设置已恢复，保留同签名同版本的调试构建。手机显示结果待刷新后确认。

## 后续维护工具

`tools/repair_device_history.py` 默认只预览。计划必须包含目标路由器序列号及每条已确认的 MAC、地址和日期。正式执行前停止对应 Hub；工具自动备份数据库、保存隔离记录并在一个事务中修改归档、事件和统计。

示例：

```bash
python /app/tools/repair_device_history.py \
  --data-dir /app/data \
  --backups-dir /app/backups \
  --plan /app/backups/confirmed-observations.json
```

核对预览后，正式执行增加 `--apply`。不要凭 SSID、网段或另一台路由器也出现过相同 MAC 就批量删除历史。

存储模块修复已写入源码，并应用于 NAS 的现有 BE72 容器。后续发布的镜像应包含该模块更新；本次没有替换现有容器的其他业务模块。
